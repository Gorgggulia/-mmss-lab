# ADR-0002. Вибір транспорту для телеметрії та подій браку

## Статус
Прийнято, 2026-09-20

## Контекст
Система має три різнорідні потоки даних між межовим вузлом і сервером:
високочастотну телеметрію вібрації та швидкості (потребує низької
накладної вартості на повідомлення), рідкісні, але критичні події браку із
зображеннями (потребують надійної доставки), та команду автоматичної
зупинки лінії (FR-09; має гарантовано дійти навіть за нестабільного
зв'язку). Цех уже має SCADA/PLC-інфраструктуру, значна частина якої
підтримує MQTT або OPC-UA.

## Варіанти
1. **Єдиний REST API для всіх потоків.** Простий у реалізації та
   налагодженні, але не підходить для потокової телеметрії з частотою
   1 кГц (накладні витрати HTTP-запиту на кожне повідомлення) і не дає
   push-доставки сповіщень без постійного опитування (polling), що додає
   затримку `L_мер`.
2. **MQTT для телеметрії та подій + окреме завантаження зображень у
   сховище.** Легкий publish/subscribe протокол з малим заголовком
   пакета та вбудованою підтримкою рівнів якості обслуговування (QoS),
   що дозволяє розрізняти критичні й некритичні повідомлення.
3. **gRPC-стрімінг для всього.** Ефективний бінарний протокол з
   двостороннім стрімінгом, але складніший в інтеграції з наявними
   PLC цеху, які здебільшого підтримують MQTT/OPC-UA, а не gRPC.

## Рішення
Обрано варіант 2. Телеметрія (вібрація, швидкість) і події браку
передаються через MQTT: QoS 0 для високочастотної телеметрії (втрата
поодинокого відліку прийнятна, див. реєстр даних), QoS 1 для сповіщень
про брак, QoS 2 — для команди зупинки лінії (FR-09), де втрата чи
дублювання неприпустимі. Самі зображення завантажуються окремим
HTTP-запитом у сховище (див. ADR-0003), а MQTT-повідомлення про подію
містить лише посилання на завантажене зображення.

## Наслідки
+ Сумісність із наявною SCADA-інфраструктурою цеху — більшість PLC вже
  підтримують MQTT, інтеграція не вимагає додаткових шлюзів.
+ Гарантована доставка критичних команд (QoS 2) навіть за короткочасних
  розривів зв'язку, що напряму підтримує сценарій QS-02.
− Потрібен окремий MQTT-брокер із резервуванням (кластер), щоб уникнути
  єдиної точки відмови для всіх ліній цеху.
− Зображення та телеметрія передаються різними каналами (MQTT і HTTP),
  що вимагає синхронізації міток часу для коректної кореляції подій
  під час аудиту (FR-07).
